# Capture, guidance and reconstruction: options and resources

Research snapshot: **September 26, 2026**. This page consolidates existing primary-source reviews and bounded local experiments. It contains no private survey criteria or customer imagery. Publisher results, local execution and proposed integrations are different kinds of evidence; none of the work establishes a validated exterior-house survey on a phone.

Read the [high-level handoff](../06-research-handoff.md) for the overall recommendation and the [experiment ledger](2026-09-26-experiment-evidence.md) for individual outcomes. This page explains the alternatives and links their primary resources.

**Recommended direction:** native iPhone capture, optional depth, local quality and guidance, durable selected photographs, asynchronous server interpretation, and explicit geometric checks. Keep a simple reviewable scene ahead of a photorealistic model. Retain Android and browser paths as meaningful alternatives with different evidence capabilities.

Evidence labels below:

- **Local:** the stated code or model path actually ran on this Mac. The fixture and scope still matter.
- **Source:** official documentation, pinned source or artifact contracts were inspected; the product integration was not run.
- **Proposed:** a design choice or next comparison, not an observed result.
- **Blocked / empty:** a preserved outcome, not a successful benchmark or proof that the underlying method is unsuitable.

## 1. Capture the exterior and useful detail

| Path | What distinguishes it | Recommendation and evidence |
|---|---|---|
| **Swift + ARKit / RealityKit** | One native session provides images, camera poses, calibration and tracking state. Supported devices can add depth and scene meshes. | **Primary path. Source + API typechecks.** Own the camera, buffers, frame metadata and overlays in native code. No physical-phone capture, outdoor accuracy or thermal result was obtained. [Tracking lifecycle](https://developer.apple.com/documentation/arkit/managing-session-life-cycle-and-tracking-quality), [scene depth](https://developer.apple.com/documentation/arkit/arframe/scenedepth). |
| **Object Capture area mode** | Automatic photos, capture feedback and a point-cloud UI for surfaces that cannot be circled. | **Native alternative for a geometry demo. Source/API inspection.** Apple's sample requires supported LiDAR hardware. The inspected public session API does not expose the same per-frame image/pose feed as an app-owned ARSession; capture and photogrammetry are separate phases. [WWDC24 area mode](https://developer.apple.com/videos/play/wwdc2024/10107/), [sample](https://developer.apple.com/documentation/realitykit/scanning-objects-using-object-capture). |
| **Android ARCore** | Tracking, planes, calibration and optional depth; supported devices can compute depth without a dedicated depth sensor. | **Credible expansion path. Source only.** Check tracking and depth support separately. Raw depth can contain holes or reproject earlier observations; it is not a ready environment mesh or an independent new measurement every frame. [Raw depth](https://developers.google.com/ar/develop/java/depth/raw-depth), [shared camera](https://developers.google.com/ar/develop/java/camera-sharing). |
| **Browser photo coaching** | Link-based entry, camera preview, framing instructions and asynchronous analysis with less installation friction. | **Useful reduced-capability alternative. Source only.** Ordinary iPhone Safari was not established as a native WebXR/ARKit pose or LiDAR-export path. Chrome Android has an ARCore-backed WebXR path, but photographic evidence/calibration export still needs a separate check. [WebKit issue](https://bugs.webkit.org/show_bug.cgi?id=309550), [Android WebXR](https://developers.google.com/ar/develop/webxr). |
| **Expo shell + native capture module** | Retains React Native screens while Swift owns the complete AR capture view and data stream. | **Integration alternative, not removal of native work. Source only.** Use a development build; Expo Go cannot load arbitrary custom native code. Send compact events/file references to JavaScript rather than every camera buffer. [Expo native code](https://docs.expo.dev/workflow/customizing/). |

Ordinary ARKit tracking and LiDAR are different capability tiers. Do not require a depth sensor merely to show spatial cues, and do not infer measured free space when depth is missing. Save each selected photograph with **its own** calibration, dimensions, timestamp and pose. ARKit's [high-resolution frame API](https://developer.apple.com/documentation/arkit/arsession/capturehighresolutionframe(completion:)) can deliver an asynchronous still during tracking; format support and the returned frame must be checked.

Useful open-source references include [Stray Scanner](https://github.com/strayrobots/scanner) (MIT; inspected recorder requires scene depth), [NeRFCapture](https://github.com/jc211/NeRFCapture) (MIT; optional-depth capture reference), and [arkit-3dgs-scanner](https://github.com/KuoFengYuan/arkit-3dgs-scanner) (Apache-2.0; automatic selection/quality code). None is a locally validated turnkey survey app.

For distribution, an [App Clip can use ARKit](https://developer.apple.com/documentation/appclip/interacting-with-app-clip-codes-in-ar), but its [capability limits](https://developer.apple.com/documentation/appclip/choosing-the-right-functionality-for-your-app-clip) include no background URLSession activity. Browser alternatives also need lifecycle testing. The 2026 [8th Wall release](https://8thwall.org/docs/open-source) opens its MIT framework, **not its SLAM engine**: the separate binary has a [different license](https://github.com/8thwall/engine/blob/main/LICENSE). [AlvaAR](https://github.com/alanross/AlvaAR) is a GPLv3 browser visual-SLAM research alternative, not a demonstrated native-equivalent phone survey engine.

## 2. Guide the person and choose photographs

**Recommended baseline:** combine current task needs, tracking quality, image quality and accepted-view history. Keep “move to another viewpoint” separate from “aim here,” “hold still” and “recover tracking.” A useful preview requests a still; progress advances only after the returned image and metadata are accepted and durably saved.

| Component | Useful resource or approach | Evidence and remaining gap |
|---|---|---|
| Blur, exposure, text size and motion checks | Native image statistics, AR tracking state and sampled [Vision OCR](https://developer.apple.com/documentation/vision/vnrecognizetextrequest). | **Source + Mac OCR probes.** No universal phone-quality threshold was established. High OCR confidence can accompany a wrong identifier. |
| Task-aware capture admission | Bounded preview analysis; one capture in flight; reassess the actual still; persist before crediting progress. | **Local synthetic protocol controls.** Save failures and interrupted transactions did not become successful captures in the tested prototype. This does not measure camera/still latency or image usefulness. |
| Fog of war | A ledger of observed surface patches and unresolved evidence tasks, supported by visible saved images. | **Local synthetic replay.** Walking a route or placing a surface inside the camera frustum does not prove that surface was seen through an occluder or at usable quality. |
| Viewpoint selection | Small candidate-view search with accepted viewing-direction history, a stable target and recovery preconditions. | **Local synthetic replay.** Hysteresis reduced scripted target switching; a wrong predicted footprint could make look-ahead worse. No homeowner-effort improvement was measured. |
| Visibility and unknown space | [Open3D ray queries](https://www.open3d.org/docs/latest/python_api/open3d.t.geometry.RaycastingScene.html); [OctoMap](https://octomap.github.io/) for free/occupied/unknown mapping. | **Source; simple synthetic geometry also exercised.** A partial mesh limits visibility claims. Open3D is MIT; OctoMap core is BSD, while its viewer has different terms. Neither is a complete phone guidance system. |
| Screen-space arrows/reticles | ARCamera projection using the correct orientation, viewport and frame; suppress unsupported world cues after a coordinate reset. | **Local API typecheck + source contract.** Signatures compiled; physical camera alignment and live cue stability remain untested. A simulator cannot validate real camera/VIO. |

Learned next-best-view systems remain alternatives, not necessary dependencies. [SEE++](https://github.com/robotic-esp/see-public) offers an MIT point-density/frontier approach with a robotics stack. [GenNBV](https://github.com/zjwzcx/GenNBV) supplies learned planning code and checkpoints, but uses a drone action space, substantial GPU/simulator resources and CC-BY-NC-SA terms. Neither was run locally. Their published benchmarks do not establish safe, accessible movement instructions for a person around a house.

## 3. Reconstruct and visualize

Use a versioned, inspectable geometry representation for measurements and a separate rendering asset for review. Metric units, photorealism, model confidence and additional photographs do not by themselves establish metric accuracy.

| Option | Actual update/output contract | Recommendation, local status and license boundary |
|---|---|---|
| **ARKit planes / optional mesh** | Device tracking and geometry updates during capture. | **Primary live spatial reference. Source/API evidence; no phone validation.** Apple platform SDK, not open-source model weights. Missing geometry remains unknown. |
| **DA3-Small** | Multi-view batch depth/camera inference; the separate streaming wrapper uses overlapping chunks and alignment. | **Small reconstruction challenger. Local CPU/MPS and real-image probes completed.** Adding a fourth view revised existing outputs, so batch results need revision handling. Small/Base weights are Apache-2.0; several larger variants are noncommercial. [Official project/model table](https://github.com/ByteDance-Seed/Depth-Anything-3). |
| **MapAnything Apache** | Set-based inference conditioned on images and optional calibration, poses or depth. Supplied geometry is conditioning, not a guaranteed fixed output. | **Leading larger calibrated-input challenger. Source/header audit + local preprocessing helpers only; no model forward.** Explicitly select [Apache weights](https://huggingface.co/facebook/map-anything-apache); the default other checkpoint is noncommercial. Roughly 4.58 GiB of F32 weights is not a measured VRAM requirement. [Code](https://github.com/facebookresearch/map-anything). |
| **LingBot-Map** | Actual causal frame processing with retained state after initialization. The demo wrapper resets state at the beginning of a run. | **Streaming research candidate. Source only.** A service must own persistent session state rather than repeatedly call the sequence wrapper. Documented CUDA/FlashInfer route; no local MPS/phone path demonstrated. Code and official weights declare Apache-2.0. [Project](https://github.com/Robbyant/lingbot-map), [weights](https://huggingface.co/robbyant/lingbot-map). |
| **MoGe-2 Small** | Single-image geometry, normals and scale-related outputs; tracking/fusion are separate. | **Compact geometry comparator. Local CPU ONNX and one exterior reference-discrepancy probe completed.** Export postprocessing and reference semantics matter; these runs did not establish house-survey accuracy. Official PyTorch weights declare MIT; retain the ONNX artifact's separate provenance. Newer MoGe-3 documents a different runtime and no macOS support. [Project](https://github.com/microsoft/MoGe), [Small weights](https://huggingface.co/Ruicheng/moge-2-vits-normal). |
| **COLMAP 4.2** | Established sparse feature reconstruction; dense geometry requires further stages. Known poses or external scale can be supplied, but do not validate themselves. | **Classical baseline. Local fixed-pose matching completed with an empty final sparse model.** Preserve that result and earlier setup failures; it is not evidence that COLMAP fails on all houses. BSD core; learned components have separate licenses/build requirements. [Tutorial](https://colmap.github.io/tutorial.html), [4.2 release](https://github.com/colmap/colmap/releases/tag/4.2.0). |
| **Apple Depth Anything V2 Small Core ML** | An image-depth package whose inspected graph normalizes by the image's own maximum. | **Native auxiliary-depth candidate. One Mac CPU compile/load/prediction completed.** It did not establish metric depth, near/far interpretation or iPhone behavior. [Official package](https://huggingface.co/apple/coreml-depth-anything-v2-small). |

Start review visuals with points, planes, footprints and evidence links. [RealityKit LowLevelMesh](https://developer.apple.com/documentation/realitykit/lowlevelmesh) and [Three.js](https://threejs.org/docs/) support changing geometry. [Rerun](https://rerun.io/docs/reference/sdk/operating-modes) is useful for synchronized engineering timelines; it is not the durable evidence store. [Spark](https://sparkjs.dev/docs/lod-getting-started/) can stream prepared Gaussian assets for rich browser review, but that is different from incrementally reconstructing the scene. Three.js/Spark are MIT; Rerun offers MIT/Apache licensing. These viewer integrations were source-reviewed, not delivered as an integrated live product. Splats are a visual representation, not guaranteed solid collision or clearance geometry.

## 4. Recognize evidence, then apply explicit checks

Recognition should produce observations linked to original images and geometry. A deterministic evaluator then consumes supported measurements, applicable published/configured rules and explicit uncertainty. A class score, mask score, tracking score and measurement-error bound are different quantities. Preserve unresolved observations and review paths rather than turning missing evidence into a favorable result.

| Need | Recommended baseline and alternatives | Evidence and adoption limit |
|---|---|---|
| Exact label text | **Apple Vision** locally; [PP-OCRv6 tiny](https://huggingface.co/PaddlePaddle/PP-OCRv6_tiny_rec) as a specialist open-source comparator. | **Both ran on the same generic synthetic fixtures on Mac.** Both produced high-score exact-string errors. PP-OCR requires detection, crop processing and recognition; its checked code/model cards are Apache-2.0. This is not field identifier accuracy or a phone-speed ranking. |
| Equipment proposals and masks | User nomination plus [Grounding DINO](https://github.com/IDEA-Research/GroundingDINO) / [SAM 2.1](https://github.com/facebookresearch/sam2); newer [SAM 3.1](https://huggingface.co/facebook/sam3.1) as a server challenger. | **Source only for these full pipelines.** DINO/SAM 2 baseline artifacts have Apache terms. SAM 3 uses a custom gated license and a larger GPU-oriented stack. A semantic phrase or mask does not prove equipment identity or absence. |
| Native image segmentation | [Apple's SAM 2.1 Tiny packages](https://huggingface.co/apple/coreml-sam2.1-tiny/tree/39ae0a8a83e5e6cd196e804bf7cccc5f8171f306); [EdgeTAM](https://github.com/facebookresearch/EdgeTAM) and [YOLOE](https://github.com/THU-MIG/yoloe) as alternatives. | **Artifact/source audits; native prompt-model execution blocked before prediction by the declared sandbox.** The Apple package card declares Apache-2.0. That is not a mask-quality failure. EdgeTAM's reviewed Core ML export omitted temporal memory and had preprocessing/input issues. YOLOE can fuse a fixed vocabulary for export, but has AGPL terms and text-model dependencies. No phone mask pipeline was validated. |
| Carry a nominated region across frames | Vision object tracking; [OpenCV ViTTrack](https://github.com/opencv/opencv_zoo/tree/47534e27c9851bb1128ccc0102f1145e27f23f98/models/object_tracking_vittrack); causal [BootsTAPIR](https://github.com/google-deepmind/tapnet). | **All ran locally on the same already-seen book clip, with different tasks.** Vision's confidence did not reliably flag observed box loss. ViTTrack returned rejected updates that must not become fresh boxes. BootsTAPIR's visible point containment was 457/1,392 overall, alongside 457/458 among declared-visible outputs—not point accuracy or box IoU. ViTTrack Zoo files and current TAPNet code/checkpoint declarations are Apache-2.0. |
| Other point-tracking alternatives | [CoTracker3](https://github.com/facebookresearch/co-tracker) and [TAPNext++](https://github.com/google-deepmind/tapnet/tree/730cda1c730877cfedbe01bf87fb1cadb78a565d/tapnet/tapnextpp). | **Source only.** CoTracker online uses windows with possible within-window look-ahead and noncommercial code/weights. TAPNext++ has a causal recurrent path and Apache declarations, but its reviewed checkpoint is much larger. Neither establishes phone deployment or physical identity. |
| Barcode corroboration | Native Vision, with [ZXing-C++](https://github.com/zxing-cpp/zxing-cpp) as an Apache-2.0 alternative. | **Local synthetic native observations plus source review.** Preserve decoded string and raw payload semantics separately; raw barcode bytes were not interchangeable with encoder UTF-8. A correctly decoded code still needs association and interpretation. |

Object masks do not supply visibility truth for each tracked physical point. Likewise, a label associated to the wrong enclosure remains wrong even when its transcription is exact. Coordinate transforms, timestamps, session/reconstruction revisions and source-image association are part of the evidence path, not optional rendering details.

## Hybrid architecture and uploads

**Recommended split:** keep preview, tracking recovery, aiming and capture acknowledgment on the device; send selected evidence for asynchronous interpretation; refine heavier geometry/render assets separately. A device-led deferred workflow is the robust offline alternative. A cloud-led stream is an experiment option when bandwidth and latency permit, not a prerequisite for immediate guidance.

The local network replay used **hypothetical workloads and latencies**. It showed why durable originals need their own queue, lost acknowledgments need idempotent reconciliation, and stale guidance should be rejected by task/coordinate dependencies. Requiring every reply to mention the newest photograph can also starve useful older findings. These are protocol observations, not measured carrier performance.

| Transport / work type | Useful resource | Decision and status |
|---|---|---|
| Durable selected images | [Background URLSession](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:)); file-backed uploads. | **Native baseline; source evidence.** OS scheduling and force-quit behavior matter. Background transfer does not keep AR capture running. |
| Resumable uploads | [TUSKit](https://github.com/tus/TUSKit), [tusd](https://github.com/tus/tusd), both MIT; [Supabase tus endpoint](https://supabase.com/docs/guides/storage/uploads/resumable-uploads). | **Candidate transport; no successful recovery-transfer result.** Local work preserved build/resource and later monitoring-permission blockers. tus and Foundation's HTTPbis resume are different protocols. Service chunk rules and iOS background scheduling still need actual integration tests. |
| Current whole-bundle service | Keep an explicit completed-asset handoff from any future resumable transport. | **Source inspection at the reviewed service revision.** A ZIP/multipart request is not already a resumable or incremental reconstruction API. |
| Periodic versus stateful reconstruction | Coalesce replaceable batch jobs; preserve ordered, deduplicated accepted inputs for a stateful model. | **Proposed architecture with synthetic controls.** Reconnection needs replay/checkpoint semantics; a socket reconnect does not restore model state. |

## What would change the recommendation

A consented physical-phone experiment remains the highest-value missing evidence: synchronized images/poses/calibration, ordinary and depth-capable capture where available, known scene measurements, glare/blank surfaces, tracking interruption and offline recovery. Simulator and desktop success cannot establish camera/VIO behavior.

Before that hardware is available, the useful next checks are a small move-versus-aim replay, a known-pose display/coordinate-reset replay, and a capability-limited walkthrough that keeps image-only evidence distinct from measured geometry. More model demos on the same seen clip would not resolve those integration gaps. All candidate licenses should be checked at the exact artifact and dependency versions selected for distribution; permissive code does not automatically license weights, datasets or hosted services.
